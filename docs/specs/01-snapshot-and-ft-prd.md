## 1. 业务目标与范围

### 1.1 解决什么问题
1. **首屏秒出事实**：在用户提交 `Team ID` 后 1 秒内拉取并整理出清晰的球队现状（15 人阵容、银行余额、可用 FT、伤停与赛程），支撑“渐进式首屏”体验。
2. **算清隐形规则账**：公开 API 不直接返回“当前可用 FT”和“初始老将真实买入价”，本模块必须按 FPL 2026/27 官方规则推算 FT，并诚实标注“估算卖出价”，为后续 Agent 决策与硬规则校验提供可信的唯一事实底座。
3. **上下文瘦身**：将官方原始 600+ 球员、每人 70+ 字段的庞大 JSON 裁剪为精简快照，避免后续塞爆大模型上下文或引入噪音。

### 1.2 本步做什么 vs 不做什么
* **做什么（In-Scope）**：
  * 解析 `Team ID` 或官方球队链接；
  * 拉取并校验 FPL 公开 API 数据；
  * 推算当前可用 FT 与每名球员卖出价；
  * 加载本地脱敏演示样例（仅限用户显式触发）；
  * 产出两份结构化数据：
    * **`TeamSnapshot`（你的 15 人球队档案）**：直接渲染到网页首屏，并作为常驻上下文喂给 AI；
    * **`FPLUniverse`（全英超 600+ 球员与赛程的本地通讯录）**：保存在后端本地内存/缓存中，**不直接喂给大模型**，专门留给 Task 2 的查询工具按需筛选 Top 10 候选人。
* **不做什么（Out-of-Scope）**：
  * 不调用 DeepSeek 大模型；
  * 不实现转会推荐、规则模拟与排首发工具（属于 Task 2）；
  * 不做 SQLite 持久化（属于 Task 4）与 HTTP 接口（属于 Task 5）。

## 3. 核心业务规则口径（重点评审）

### 3.1 免费转会名额（FT）推算规则
公开 API 不直接提供当前 FT，必须从**真实建队轮次（`started_event`）**起按赛季历史逐轮推算：
1. **初始值**：在 `started_event` 当轮建队时，初始可用 FT 记为 `1`（进入下一轮前不额外滚存超出）。
2. **逐轮滚存（遍历 `started_event` 之后至当前轮之前已完成的每一轮）**：
   * **普通轮次**：先扣除该轮实际使用转会数 `event_transfers`（最低扣到 0，超出部分已在当轮扣 4 分），再获得下轮新增的 `1` 个 FT，上限封顶 `5` 个：
     `next_ft = min(5, max(0, prev_ft - event_transfers) + 1)`
   * **使用 `wildcard` 或 `freehit` 芯片的轮次**：按 2024/25 起生效的官方新规，使用这两种芯片时**保留原有 FT 不清零、也不额外 +1**，即 `next_ft = prev_ft`。
3. **人工校准标记**：默认 `ft_is_calibrated = False`；后续若用户在前端手动修改 FT，则由上层覆盖该值并置 `ft_is_calibrated = True`。

### 3.2 球员卖出价（Selling Price）折算规则
FPL 公开 API 返回的价格单位为整数“十分之一百万”（如 `105` = `£10.5m`），计算时统一用整数 `0.1m` 单位防浮点误差，对外展示保留 1 位小数：
1. **赛季中途转入的球员**（可在官方 `transfers` 接口查到最近一次 `element_in_cost` 作为 `buy_price`）：
   * **涨价了（`now_cost > buy_price`）**：官方只分一半涨价利润并**向下取整到 `£0.1m`**。
     例：买入 `£10.0m`（100），现价 `£10.3m`（103），利润 3 个 0.1m，分一半向下取整为 1 个 0.1m → 卖出价 `£10.1m`。
   * **未涨价或跌价（`now_cost <= buy_price`）**：卖出价等于现价 `now_cost`。
   * 标记：`price_is_estimated = False`（精确已知）。
2. **建队初始阵容且从未卖出/再买入的老将**（`transfers` 中无记录，已拍板采用 **方案 A**）：
   * **为什么算不准**：FPL 公开 API 不记录你开局建队那 15 个人分别是多少钱买的，只知道他们现在的市价 `now_cost`。
   * **方案 A 兜底逻辑（假设买入价 = 现价，即“没赚也没赔”）**：直接以当前市价 `now_cost` 作为估算卖出价，并严格标记 **`price_is_estimated = True`**。
   * **具体举例**：假设第 1 轮开赛时你花 `£10.0m` 买了萨卡并一直留到第 12 轮，如今萨卡涨价到了 `£10.6m`。按官方“利润对半分”规则，你在官网实际只能卖 `£10.3m`；但因为公开接口查不到你的 `£10.0m` 买入价，系统暂按 `£10.6m` 估算并标出**“估算（可微调）”**提示——如果预算卡在 `£0.1m~£0.3m` 边缘，用户在界面上手动改成 `£10.3m` 即可。
   * **取舍记录**：相比去猜第 1 轮开局初价，方案 A 规则最简单透明，代价是对大涨的初始老将会偏乐观高估一半涨幅，因此必须配合显式“估算”标签与手动校准。

### 3.3 赛程难度（`next_3_fdr`）与目标轮次（`gw`）口径
* **目标轮次 `gw`**：取官方 `bootstrap-static` 中标记为 `is_next = True` 的即将开赛轮次作为决策轮次；用于拉取最新已锁定阵容 `picks` 时，取 `is_current = True` 的最近一轮。
* **未来 3 轮赛程（`next_3_fdr`）**：从 `gw` 起算，提取该球员所在球队接下来最多 3 场英超联赛的对手简称、主客场（`H`/`A`）与官方 FDR 难度值（1~5）。若遇到双赛周（DGW）或轮空周（BGW），如实保留该轮多场或空场信息。

## 4. 关键数据对象（面向 PM 的字段字典）

### 4.1 `TeamSnapshot`（球队快照，首屏渲染与 Agent 常驻上下文）
| 字段 | 类型 | 含义 | 来源 / 说明 |
| :--- | :--- | :--- | :--- |
| `team_id` | int | 球队 ID | 用户输入 |
| `team_name` | str | 球队名称 | 官方 `entry/{id}` |
| `gw` | int | 本次决策面向的轮次（即将开赛轮） | 官方 `events`（`is_next`） |
| `picks_gw` | int | 当前阵容快照来自哪一轮 | 官方 `events`（`is_current`） |
| `started_event` | int | 真实建队轮次 | 官方 `entry/{id}` |
| `bank` | float | 银行余额（£m，如 `7.9`） | `entry_history.bank / 10` |
| `free_transfers` | int | 当前可用 FT（1~5） | 规则推算或人工校准 |
| `ft_is_calibrated` | bool | FT 是否经过人工校准 | 默认 `False` |
| `available_chips` | list[str] | 当前仍可用的芯片概览 | 对比总芯片与 `chips` 已用记录 |
| `players` | list[`PlayerSnapshot`] | 15 名球员精简清单 | 见下表 |

### 4.2 `PlayerSnapshot`（15 人精简球员字段）
| 字段 | 含义 | 备注 |
| :--- | :--- | :--- |
| `id` / `name` / `team` / `pos` | 球员 ID、简称（`web_name`）、球队缩写（如 `ARS`）、位置（`GKP/DEF/MID/FWD`） | 确定性映射 |
| `now_cost` | 当前市场买入价（£m） | `now_cost / 10` |
| `selling_price` | 卖出可得金额（£m） | 见 3.2 折算规则 |
| `price_is_estimated` | 卖出价是否为估算值 | `True` 时前端需标“估算” |
| `status` / `chance_of_playing` / `news` | 状态（`a` 可用 / `d` 存疑 / `i` 伤病 / `s` 停赛）、出场概率、官方简讯 | 直接来自官方 |
| `form` / `ppg` | 近况场均分 / 赛季场均分 | 直接来自官方 |
| `next_3_fdr` | 未来 3 轮赛程简要列表（如 `["WHU(A,2)", "MCI(H,4)", ...]`） | 确定性拼接 |
| `is_starter` / `bench_order` / `is_captain` / `is_vice_captain` | 当前轮次是否首发、替补顺位（0 为首发，1~4 为替补）、是否正副队长 | 来自最近一轮 `picks` |

## 5. 异常场景与提示文案规范

| 异常场景 | 触发条件 | 系统确定性动作 | 对外报错文案（供前端展示） |
| :--- | :--- | :--- | :--- |
| **输入格式非法** | 空字符串、非数字且非有效官网链接 | 拒绝请求，不发外部 API | `请输入有效的纯数字 Team ID 或 FPL 官网球队链接。` |
| **Team ID 不存在** | 官方返回 `404` | 中止加载，不切换样例 | `未找到 Team ID 为 {id} 的球队，请检查 ID 是否正确。` |
| **官方接口超时 / 限流 / 维护** | 请求超时（默认 10s）、`429`、`503` | 中止加载，保留重试入口，**不切换样例** | `FPL 官方接口暂时不可用或超时（{status}），请稍后重试。` |
| **赛季未开赛 / 无阵容数据** | `current_event` 为空或 `picks` 404 | 中止加载并明确提示 | `该球队当前暂无可用阵容快照（可能尚未完成建队或赛季未开始）。` |
| **关键字段缺失** | 官方 JSON 缺少核心字段 | Pydantic 校验拦截 | `官方返回数据格式异常，无法解析球队快照，请重试。` |

## 6. 验收标准（Acceptance Criteria）

交付本模块时，必须通过以下三类自动化测试（`pytest tests/test_fpl_client.py`）：
1. **正常 Case**：
   * 分别用纯数字 ID 和官网完整 URL 都能正确提取 `team_id`；
   * 途中转入球员若涨价 `£0.3m`，卖出价准确只算 `£0.1m` 利润且 `price_is_estimated=False`；初始老将 `price_is_estimated=True`；
   * `TeamSnapshot` 严格包含 15 名球员，字段精简无冗余。
2. **边界 Case**：
   * 非第 1 轮建队（如 `started_event = 5`），FT 从第 5 轮起算而非从第 1 轮起算；
   * 连续多轮不转会，FT 正确封顶在 `5`；
   * 某轮使用 `Wildcard` 时，原有累积 FT 不被清零也不额外 +1；
   * 显式传入 `demo=True` 时，离线样例能稳定加载。
3. **失败 Case（故障注入）**：
   * 输入 `"abc"` 或无效链接 → 立即抛出输入错误；
   * 模拟官方 API 返回 `404`、`503`、或请求超时 → 抛出明确中文错误，且**未**返回样例球队数据。
